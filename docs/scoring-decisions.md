# Обоснование решений scoring, версия 1.2

Область ответственности: предполагаемые роли, поддержка гипотез, приоритет,
числовые объяснения и проверки этих вычислений. Основа требований — ТЗ Freedom
и переданный командный план v1.1 от 23 сентября 2026, раздел 7.
Пороговые значения не взяты из банковской статистики: это начальные условия плана.

## Разделение ответственности

| Решение | Зачем и какое ограничение остаётся |
|---|---|
| Принимать готовые NodeFeatures | Модуль A единственный рассчитывает граф и метрики; исключаем две конкурирующие реализации |
| Не менять граф/API/общие DTO | Эти файлы принадлежат другим участникам; локальный адаптер будет сопоставлен их формату при интеграции |
| Удалить reference-граф из тестового harness | Даже проверка нашей части теперь принимает готовые признаки, не повторяя работу участника A |
| Три файла roles/ranking/explanations | Изменение формулировки не меняет формулу; роль и очередь можно проверять отдельно |
| Только стандартная библиотека в scoring | Расчёты малы и полностью детерминированы; дополнительных установок и внешних сервисов не требуется |
| Правила вместо обучения/LLM | Ролевых меток для обучения и оценки accuracy нет. Числовое правило можно защитить на любом gid |
| dataclass с явными типами и проверками | Ошибки единиц, gid, дат и пропусков обнаруживаются на границе, а не маскируются неверным скором |
| Возвращать записи, не писать файлы | Экспорт и публикация единого снимка остаются ответственностью общего пайплайна |

## Роли: основание логики и границы вывода

- **Consolidator:** несколько входящих ветвей сходятся в узле. Минимум 3 плательщика
  и fan-in/несколько seed уменьшают срабатывание на обычную одиночную цепочку.
  3, коэффициент 2 и минимум 2 seed — гипотезы командного плана, не доказанные оптимумы.
- **Distributor:** выраженный fan-out (>=5 получателей, >=2 раза больше входящих).
  Выявляет направление распределения; число получателей само по себе не означает нарушение.
- **Transit:** есть обе стороны потока, наблюдаемый out/in в [0.8,1.2].
  Это совместимость объёмов, а не доказательство прохождения одних и тех же денег.
  Для seed правило отключено из-за отсутствующего внешнего входа.
- **Terminal:** вход есть, исходящих операций нет, узел не на границе и не seed;
  последнее поступление не в последние два дня периода. Двухдневное окно уменьшает
  эффект поздних поступлений, но не устраняет неполноту месячной/внутрибанковской выборки.
- **Coordinator:** несколько seed-ветвей, обе стороны потока, высокое посредничество
  и соседи из разных сообществ. Несколько независимых структурных условий снижают
  риск назвать координатором любого крупного получателя. Это кандидат на проверку.
- **Peripheral:** ни одна гипотеза не достигла допуска. Это не «безопасный клиент»;
  граница, недостаток данных или простое поведение тоже приводят к этой роли.

Правила опираются на уже вычисленные метрики. Scoring не вычисляет ни пути,
ни посредничество, ни сообщества. Определения и качество этих признаков согласуются с A.

## Выбор роли и оценки

| Решение | Обоснование |
|---|---|
| Отдельные eligibility и support | Сначала проверяем необходимые условия, затем силу поддержки; высокий частный признак не обходит запрет |
| Несколько кандидатов одновременно | Финансовая роль не обязательно единственная; сохраняем альтернативы, а не скрываем их |
| Насыщение s(x,t) на 1 | Разные шкалы становятся сопоставимы; очень большая сумма/степень не создаёт неограниченный вклад |
| Равное среднее внутри support | Прозрачная базовая комбинация из плана; данных для обучения весов нет |
| Допуск support>=0.5 | Порог плана, не вероятность. Проверен на чувствительность 0.4/0.6 |
| Максимальная support | Основная роль имеет наибольшую поддержку среди прошедших все ограничения |
| Фиксированный порядок при равенстве | Результат не зависит от порядка строк/словаря; порядок из плана, не скрытая оценка важности |
| Потолки role_score | Не даём слишком уверенную гипотезу при неполноте/конкурирующих ролях |
| role_score изолята=0, fallback=0.2 | Явно отражаем слабое основание; 0.2 — условная шкала из плана, не калиброванная вероятность |

Нормировочные константы 8/3/15/5 и потолки 0.5/0.55/0.75/0.6 взяты из раздела 7.2
командного плана. У них есть интерпретируемая функция, но нет внешнего подтверждения
оптимальности. Они версионированы, видны в коде и документации; менять их скрытно нельзя.

## Приоритет проверки

Формула плана: 0.35×seed_reach + 0.25×role_support + 0.25×betweenness + 0.15×volume.
Она сочетает связь с исходными ветвями, структуру поведения, посредничество и объём.
Оборот имеет меньший вес, чтобы большая сумма не определяла весь список.
**Точные веса — не научно установленное соотношение.** Они подлежат командному ревью.

Приоритет не умножается на role_score: неполнота данных может быть причиной
дополнительной проверки. Иначе обрезанные узлы исчезали бы из внимания автоматически.
Все четыре вклада доступны в объяснении. При равенстве выбираем порядок gid по возрастанию.
Top-30 даёт запас относительно обязательного top-20; на маленьком тестовом входе
не создаём выдуманных клиентов для достижения 20 строк.

Процентили считаются только среди положительных значений полного набора. Нули — 0,
одинаковые значения получают средний ранг. Это устраняет произвольное различие
между одинаковыми метриками. Расчёт на фильтре интерфейса запрещён: он поменял бы шкалу.

## Точность и неполные данные

| Решение | Предотвращаемая ошибка |
|---|---|
| Целые тиыны на входе | Потеря копеек при float-агрегации; перевод KZT→тиыны делает модуль A |
| Fraction для денежного сравнения | Значение на 1 тиын вне допустимого диапазона не округляется на границу float |
| Float только в нормированных score | Шкале поддержки не требуется бухгалтерская точность; деньги остаются целыми |
| terminal требует out_tx=0, не только out_degree=0 | Перевод самому себе не создаёт контрагента, но остаётся исходящей операцией |
| depth=4 без исходящих запрещает terminal | Обрыв выгрузки не выдаётся за оседание средств |
| Неизвестная дата/активные дни не заменяются нулём | Отсутствие признака не становится ложным подтверждением terminal |
| Конец периода передаётся явно | Последний наблюдаемый перевод не равен концу окна сбора |
| Все входные gid сохранены, повторы gid отклоняются | Не теряем изоляты и не создаём два противоречивых решения одному клиенту |
| gid/деньги строками в объяснении JSON | Browser/JavaScript не округляет большие int64 при передаче в UI |
| Полный набор условий и конфигурация в объяснении | Возможно восстановить причину результата и проверить версию правил |
| Evidence<=200 без слепого обрезания | Критическое предупреждение не исчезает ради длины поля |

Сохранение совпадающих транзакций, валидация Parquet и подсчёт денег — зона A;
наш код принимает итоговые признаки и не дедуплицирует исходные данные.

## Использование готовых решений

Используются `dataclasses`, `datetime`, `fractions.Fraction`, `bisect`, `json`,
`unittest`, `decimal` (в сценариях чувствительности). Самописные алгоритмы графов
из нашей зоны исключены. Binary-search функции стандартного Python заменили
ручной обход диапазонов совпадающих рангов.

- Документация bisect: https://docs.python.org/3/library/bisect.html
- Для проверки семантики среднего ранга изучена документация SciPy rankdata:
  https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.rankdata.html

SciPy не добавляли в зависимости только ради небольшой функции: диапазоны равных
значений находятся стандартным bisect, а наша формула сохраняет точное сравнение
целых денежных сумм. Сторонний исходный код не копировался.
Общие графовые библиотеки выбирает и подключает ответственный за граф участник.
При первой проверке обе удалённые ветки графа указывали на initial commit.
При последующей проверке появился код A в codex/data-graph (3651a714). Его
features.py и контракт прочитаны; добавлен адаптер Timestamp/NaT и observation_flags.
Граница depth=4 учитывается даже при известных исходящих, согласно семантике A.
Код графа не изменён; его алгоритмы не дублируются.

## Доказательства и оставшиеся ограничения

Проверяются 25 сценариев, включая пограничные денежные отношения, self-loop,
int64 JSON, роли, ограничения наблюдения, порядок входа, некорректные данные,
ранги и запуск проверки готового JSON без библиотек графов.

На reference-признаках реальных 2 248 узлов до удаления временного графового
harness выполнены 16 вариаций по одному параметру. Состав top-20 сохранялся,
число сменивших роль клиентов — от 0 до 109. Это не проверка точности ролей,
не проверка порядка внутри top-20 и не проверка устойчивости методов графа.

Пока не выполнены: интеграция с итоговым модулем A, калибровка на размеченных
ролях (меток нет), проверка на другом периоде/банке, оценка ложноположительных
выводов специалистом AML. Поэтому утверждение «ошибок нет» или «все роли правильные»
не обосновано. Обоснованы конкретные пройденные проверки и явно заданные ограничения.
