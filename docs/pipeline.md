# Пакетный запуск и контракт B → C

Версия `moneygraph.snapshot.v1`, поддержана опубликованным C `a749d9c`, 23 сентября 2026. Владелец этих изменений — наша
часть B. Граф, загрузчик, валидация и их документация перенесены из коммита коллеги
`3651a714` без изменений. API/frontend и координация команды остаются у C.
Ни main, ни ветки A/C не изменяются. Для интеграционного теста C используется
отдельная временная копия, проверенная по Git blob SHA; она не коммитится в B.

## Границы кода и причины решений

| Файл | Ответственность и причина |
|---|---|
| `moneygraph/config.py` | Проверенные параметры и неизменяемый RolePolicy; период не выводится из последнего перевода |
| `moneygraph/pipeline.py` | Только последовательность готовых функций A и B; графовые алгоритмы не дублируются |
| `moneygraph/io/exports.py` | Сериализация и гипотезы кластеров; расчёт ролей не зависит от файлового формата |
| `moneygraph/io/snapshots.py` | Хеши, завершённые снимки, атомарный указатель, проверенное чтение |
| `moneygraph/__main__.py` | Параметры запуска, код возврата и путь результатов; API не реализуется здесь |
| `tests/pipeline/` | Сквозные контракты, точность gid/денег и сохранение результата при сбоях |

NetworkX, pandas и PyArrow уже использует коллега — используем те же библиотеки.
CSV, JSON, временные каталоги и хеши реализованы средствами стандартной библиотеки.
База данных и очередь задач для 2 248 узлов не нужны: завершённого локального снимка
достаточно для пакетного расчёта и чтения API. На больших объёмах это решение
потребует профилирования; текущая реализация держит весь набор в памяти.

## Запуск и параметры

```bash
python -m moneygraph run --data ./data --out ./out
python -m moneygraph run --help
```

Параметры CLI: `--period-start`, `--period-end`, `--resolution` (1.0), `--seed` (42),
`--top-limit` (30, не меньше 20). На небольших синтетических наборах top содержит
всех клиентов. Параметры betweenness и порог суммы можно передать из Python через
`PipelineConfig`; глубина фиксирована в 4, поскольку правила B рассчитаны на этот кейс.
Все параметры попадают в manifest. Для чувствительности правил используется
существующий `tests/scoring/validate_features.py`; CLI не добавляет свой редактор правил.

## Файлы и единицы

Обязательные CSV имеют ровно обязательные колонки ТЗ:

- `nodes_roles.csv`: `gid,role,role_score,cluster_id,priority_score,evidence`;
- `clusters.csv`: `cluster_id,n_nodes,n_seed,sum_kzt_internal,top_gids,hypothesis`;
- `top_nodes.csv`: `rank,gid,role,priority_score,why`.

CSV: UTF-8, заголовок, разделитель запятая. `gid` записан точным десятичным целым;
при чтении в JavaScript или Excel его следует сохранять как строку.
`sum_kzt_internal` — десятичная запись KZT с двумя знаками, полученная из целых
тиынов без float. `top_gids` — JSON-массив строковых gid, до пяти участников
кластера по приоритету. Hypothesis следует из состава ролей, содержит счётчики,
число seed, число узлов границы, внутренний и межкластерный входящий/исходящий
оборот, три ведущих gid с ролью и приоритетом. Внутренняя сумма статистики A
дополнительно сверяется с направленными рёбрами. Гипотеза не устанавливает незаконность
переводов и не доказывает единую организацию.

`features.parquet` сохраняет полную таблицу A: gid, признаки денег/связей,
наблюдаемость, seed_paths, даты, метрики и cluster_id. Это признаки, без ролей.
`transactions.parquet` содержит `src,dst,date,sum_kzt,sum_minor,tx_ref`;
для расчётов использовать целый `sum_minor`. `tx_ref` — индекс исходной строки,
действителен только внутри данного run_id. Повторяющиеся операции сохранены.
Добавляем этот файл, чтобы C не зависел от отдельно меняющихся исходных Parquet.

`graph.json`: объект с `directed=true`, `currency="KZT"`, `scale=2`, массивами
`nodes` и `edges`. Узлы содержат все признаки A и шесть полей nodes_roles;
рёбра — `src,dst,sum_minor,n_tx,depth`. В JSON все gid (включая seed_paths) и
денежные значения в тиынах — **строки**. Даты — ISO `YYYY-MM-DD`, отсутствующие
метрики — `null`, NaN/Infinity отсутствуют. Числовые счётчики и cluster_id — числа.

`explanations.jsonl`: одна JSON-запись `ScoredNode.explanation_record()` на gid;
содержит `features`, `assignment`, `priority_score`, `evidence`, `factors`,
`contributions`, `policy`, `currency`, `scale`, `rules_version`.
Общие run_id/schema_version находятся в manifest и передаются наружу слоем API.

`quality.json` сохраняет проверки A и ограничения выборки. `manifest.json`
содержит `schema_version`, `run_id`, `identity`, `artifacts`, `counts`, `currency`,
`scale`, `graph_metadata`, `warnings`, `timings_seconds`, `period`, `rules_version`,
`demo=false`. period содержит start/end в ISO. Сохраняется ранее опубликованное
имя схемы `moneygraph.snapshot.v1`: новая версия C уже поддерживает его, поэтому
переименование в синтетический формат 1.0 не требуется. Ранее созданные снимки
остаются читаемыми; файлы опубликованных запусков не редактируются на месте.
Денежные поля в JSON метаданных тоже строковые. `through_exports` измеряет время
до завершения записи результатов; печатаемое CLI время включает проверку хешей
и публикацию; `output_validation` — повторное чтение и сверка всех артефактов.
При повторном запуске manifest первого снимка не перезаписывается.

## Как подключиться участнику API

```python
from pathlib import Path
import json
import pandas as pd
from moneygraph.io.snapshots import open_current

snapshot = open_current(Path("out"))  # проверяет все SHA-256 один раз при открытии
run_id = snapshot.run_id
graph = json.loads(snapshot.artifact("graph.json").read_text(encoding="utf-8"))
features = pd.read_parquet(snapshot.artifact("features.parquet"))
transactions = pd.read_parquet(snapshot.artifact("transactions.parquet"))
nodes_csv_path = snapshot.artifact("nodes_roles.csv")

from moneygraph.api import create_app
app = create_app(snapshot.directory)  # передаём Path, а не dataclass-локатор B
```

`AnalysisSnapshot` — frozen dataclass с `directory: Path`, `run_id: str` и
`artifact(name) -> Path`; метод разрешает только известные имена файлов.
Можно открыть конкретную папку через `open_snapshot(path)`.
API закрепляет один snapshot на срок жизни приложения/сессии; нельзя на каждом
запросе независимо перечитывать current и смешивать роли одного запуска с графом
другого. Совместный прогон с C `a749d9c` выполнен на настоящем каталоге, без
промежуточного адаптера и без заглушек. В CLI есть `--serve`, `--port` и
`--static-dir`: вызывается публичный `moneygraph.api.create_app`, затем Uvicorn
на 127.0.0.1. Собственного сервера или HTTP-маршрутов B не добавляет.
Перед create_app CLI ещё раз вызывает open_snapshot. В новой версии C его
собственный загрузчик проверяет хеши и закрепляет именно прочитанные байты,
также сверяет операции с рёбрами и внутренние суммы кластеров. Проверка работает
и при самостоятельном `python -m moneygraph.api --snapshot ...`.

## Воспроизводимость и публикация

run_id — SHA-256 канонического JSON из хешей исходных файлов, конфигурации,
версии правил, SHA-256 исходников расчётного пакета и фактических версий Python,
numpy, pandas, pyarrow, networkx, scipy, ОС и архитектуры. Локальные изменения кода
тоже меняют идентификатор; метка Git сама по себе недостаточна.
Транзитивные зависимости не объявляются полным lockfile: фиксированы расчётные
библиотеки. При обновлении окружения повторно прогоняются тесты и замеры.

Все артефакты сначала пишутся в отдельный временный каталог внутри `out/runs`.
Каждый записанный CSV/Parquet/JSON читается обратно и сверяется с проверенными
входами, полной таблицей признаков и результатом scoring. Проверяются суммы
и число операций рёбер, принадлежность/агрегаты кластеров, роли/ранги,
explanations и метаданные. JSON-сравнение различает целые, float и bool;
ненулевое время суток не обрезается до даты. Затем после проверки состава и
SHA-256 каталог переименовывается в `out/runs/<run_id>`;
`current.json` заменяется последним через `os.replace`. При сбое загрузки,
экспорта или обновления указателя прошлый снимок остаётся доступен. Завершённый
снимок, записанный до сбоя указателя, допустимо оставить на диске: повторный
запуск проверит его и опубликует указатель.

Одинаковый запуск заново вычисляет результаты и сравнивает хеши с уже существующим
снимком. Расхождение или повреждённый файл вызывает ошибку, а не тихую перезапись.
Два одновременных одинаковых запуска могут оба выполнить расчёт, но публикуют один
согласованный снимок. При разных входах current указывает на последний успешно
завершившийся запуск. Протокол рассчитан на локальную файловую систему и сбои
процесса; полная устойчивость к отключению питания или особенности сетевых ФС
не заявляются. Ручное редактирование опубликованных артефактов не поддерживается.
