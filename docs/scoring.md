# Скоринг: роли, приоритет и объяснения

Статус: реализован независимый модуль роли B. Ветка `codex/scoring-rules`.
Основа: командный план v1.1, раздел 7. Версия правил `roles-v1.2`.
Это инженерные гипотезы для проверки аналитиком, не банковская модель виновности.

## Границы изменений

- `moneygraph/analytics/roles.py`: локальный тип входа, валидация и правила ролей.
- `moneygraph/analytics/ranking.py`: пакетный скоринг, разложение приоритета, записи для экспорта.
- `moneygraph/analytics/explanations.py`: короткие числовые объяснения.
- `tests/scoring/`: проверки поведения и проверка готового снимка признаков.

Графовые алгоритмы и API не изменены. По последующему назначению добавлен общий
пакетный запуск, экспорт и снимок: см. [pipeline.md](pipeline.md).
Namespace-пакеты импортируются из корня репозитория без изменения общих `__init__.py`.
Модуль работает на стандартной библиотеке Python 3.12. Никаких сетевых запросов, LLM,
внешних данных, обучения или зашитых gid. Этот модуль не выпускает `clusters.csv`,
не создаёт snapshots и не заменяет весь продукт.

## Контракт интеграции

Фасад: `score_nodes(features, period_end=..., policy=RolePolicy()) -> list[ScoredNode]`.
Вход — полный набор узлов периода, а не отфильтрованная выборка интерфейса.
Порядок результата — gid по возрастанию. Входные объекты не изменяются.
Локальный `NodeFeatures` служит адаптером до появления общих DTO тимлида.

| Поля NodeFeatures | Что передаёт модуль A |
|---|---|
| gid, depth, is_seed, cluster_id | Исходный int64 gid, depth 0..4, bool; назначенный cluster_id >=0 |
| in_degree, out_degree | Число уникальных контрагентов без самого узла |
| in_minor, out_minor | Точные целые тиыны, не float KZT; суммы включают наблюдаемые операции |
| in_tx, out_tx | Количество операций; совпадающие строки не удаляются |
| reachable_seeds | Число разных seed с направленным путём до 4 переходов; сам узел исключён |
| betweenness | Неотрицательная нормированная направленная центральность [0,1] |
| other_neighbor_clusters | Число разных сообществ соседей, кроме собственного |
| active_in_days | Число дней поступлений; None если не рассчитано |
| last_in_date | datetime.date последнего поступления; None если неизвестна или входа нет |
| temporal_transit_confirmed | По умолчанию False; True только при обоснованном сопоставлении по датам |

Отсутствие структурных признаков вызывает ошибку входа, не скрытую подстановку нуля.
Неизвестные temporal-поля отключают terminal, которому нужны эти сведения.
Отсутствие подтверждения транзита по датам ограничивает confidence.
`period_end` передаётся из метаданных периода: его нельзя вычислять как последнюю
наблюдаемую операцию, иначе изменится окно наблюдения.
Для pandas сначала преобразуйте даты в date, numpy.bool_ в bool, пропуски в None.
Адаптер не должен переименовать KZT в minor без точного пересчёта денег.

```python
from datetime import date
from moneygraph.analytics.roles import from_feature_record, RolePolicy
from moneygraph.analytics.ranking import score_nodes, top_records

# feature_table — DataFrame из compute_features участника A.
features = [from_feature_record(record)
            for record in feature_table.to_dict(orient="records")]
scored = score_nodes(features, period_end=date(2026, 7, 31), policy=RolePolicy())
node_rows = [node.csv_record() for node in scored]
top_rows = top_records(scored, limit=30)
explanations = [node.explanation_record() for node in scored]
```

`csv_record` выдаёт ровно gid, role, role_score, cluster_id, priority_score, evidence.
`top_records` выдаёт rank, gid, role, priority_score, why. Лимит >=20;
на маленькой синтетической выборке выдаёт все доступные узлы. Повторные gid запрещены.
Запись CSV и публикация снимка выполняются отдельно, в `moneygraph.pipeline`.
`explanation_record` JSON-совместим: даты ISO, gid и деньги строками,
currency=KZT, scale=2, полная конфигурация policy, версия правил, все кандидаты,
проверенные условия, нормированные факторы, потолки уверенности и ограничения.
Это внутренний payload, не готовый HTTP DTO: run_id/schema_version добавляет слой снимка/API.

## Формальные правила

s(x,t)=min(max(x,0)/t,1). Support — среднее перечисленных слагаемых.
Правило допуска и support>=0.5 должны выполняться одновременно.

| Роль | Допуск по умолчанию | Слагаемые support |
|---|---|---|
| consolidator | in_degree>=3 и (in_degree>=2×max(out_degree,1) или reachable_seeds>=2) | s(in_degree,8), s(reachable_seeds,3), s(in_degree/max(out_degree,1),3) |
| distributor | out_degree>=5 и out_degree>=2×max(in_degree,1) | s(out_degree,15), s(out_degree/max(in_degree,1),3) |
| transit | Вход и выход; не seed/граница; out_minor/in_minor в [0.8,1.2] | max(0,1−abs(ratio−1)/0.2), s(min(in_degree,out_degree),3) |
| terminal | Есть вход, нет исходящих операций (включая self-loop); depth<4; не seed; известны активные дни и последнее поступление <=period_end−2 дня | s(in_tx,5), s(active_in_days,3) |
| coordinator | >=2 seed; вход и выход; положительная betweenness с процентилем >=0.9; >=2 других сообществ соседей | percentile(betweenness), s(reachable_seeds,3), s(other_neighbor_clusters,3) |
| peripheral | Нет принятого кандидата | 0; это отсутствие поддержки роли, не безопасность |

Максимальная support определяет основную роль. При равенстве:
coordinator → consolidator → distributor → transit → terminal.
Все пять результатов проверок сохранены, включая отклонённые кандидаты.

Role_score ограничивает support: terminal<=0.5; transit<=0.55 без временного
подтверждения или <=0.75 с ним; depth_boundary<=0.6; разница support двух
принятых лидеров <0.1 даёт <=0.6. Применяется минимальный потолок.
Для peripheral score=0 у изолята и 0.2 в остальных случаях.
Это не вероятность роли и не вероятность преступления.

Процентиль положительных значений: средний 1-based ранг / количество положительных
значений. Нули имеют 0. Например [0,10,10,20] → [0,0.5,0.5,1].
Сравнение денежных объёмов выполняется на integer minor units без потери int64-точности.

priority = 0.35×S + 0.25×M + 0.25×B + 0.15×V:
S=s(reachable_seeds,3); M=max принятой support или 0; B=процентиль betweenness;
V=процентиль max(in_minor,out_minor). При равном приоритете меньший gid идёт первым.
Проверка выбора support против caps выполнена на настоящем снимке:
в двух top-20 совпадают 7 узлов; подробности и воспроизводимый запуск —
[scoring-sensitivity.md](scoring-sensitivity.md). Это существенная зависимость
от цели очереди, а не основание заявлять точность классификации.
Confidence не умножается на priority: недостаток данных не означает низкую важность.
Веса и нормировочные константы фиксированы версией кода; пороги допуска изменяются
через RolePolicy и сохраняются в подробном объяснении. При смене формул нужна новая версия.

Короткое evidence содержит наблюдаемые числа и главное ограничение, <=200 символов.
Подробное объяснение содержит все ограничения. `why` дополнительно показывает четыре
взвешенных вклада в приоритет. Текст не обрезается с потерей предупреждения.

## Проверки

Без дополнительных зависимостей, из корня проекта:

```bash
python -B -m unittest discover -s tests/scoring -v
```

25 behavioral-тестов: все роли, неоднозначность, изоляты, seed, граница, отсутствующие
даты, конец другого месяца, неверный ввод, нулевой вход, точность больших integer-сумм,
детерминизм, ранги, JSON-сериализация и разложение приоритета.

Проверка готовых признаков, переданных участником A:

```bash
PYTHONPATH=. python -B tests/scoring/validate_features.py features.json --sensitivity
```

Вход JSON: `{"period_end":"2026-07-31","features":[...]}`. Элементы features —
поля NodeFeatures из таблицы выше; last_in_date — ISO-дата или null. gid и суммы
передаются JSON integers для чтения Python (не через браузер); bool — true/false.
Проверка не строит граф, не считает центральности и не назначает кластеры.
Временный reference-графовый harness удалён: расчёты признаков принадлежат A.

Исторический прогон на reference-признаках выданного набора до удаления harness:
2 248 узлов сохранены, включая 19 изолятов; ни одного terminal на границе и
ни одного transit/terminal у seed. Роли: consolidator 103, distributor 107,
transit 42, terminal 148, coordinator 18, peripheral 1830. Максимальная длина
короткого evidence — 112 символов. Версия 1.1: скоринг около 0.131 с.
Это не замер командного пайплайна и не результат интеграции с кодом A.

16 вариаций порогов на фиксированных reference-признаках: в каждом варианте
состав top-20 сохранился (порядок внутри не проверялся), изменились роли 0–109
узлов. При minimum_support=0.6 сменились роли 109/2248, около 4.85%.
Пороги варьировались по одному на ±20%; целые минимумы округлялись вверх,
ограниченные доли отсекались на 1.0; варианты без изменения пропускались.
Это локальная проверка чувствительности, а не подтверждение правильности.
Эта историческая проверка чувствительности сохраняется отдельно от новой
проверки совместимости: 28 тестов не повторяют перебор порогов.

Ограничения: эвристики не откалиброваны; точные потоки денег не восстанавливаются;
нет данных вне выборки. Временное подтверждение при проверке отключено.
Пороговые значения и веса требуют ревью; размеченной истины нет.
Обоснования всех принятых решений: `docs/scoring-decisions.md`.

## Сверка с опубликованным модулем A

Проверен `codex/data-graph`, коммит `3651a714edd8bd5ca712b3844e9c254a029913db`:
прочитаны features.py и docs/graph-methodology.md. Путь и поля совпадают с нашим
контрактом. `from_feature_record` принимает записи DataFrame: преобразует
Timestamp/NaT, сохраняет observation_flags, игнорирует дополнительные метрики,
проверяет согласованность depth_boundary/isolated. Его код не скопирован и не изменён.

В версии 1.2 depth_boundary означает любое depth=4, в том числе при наличии
нескольких известных исходящих рёбер. Такие узлы не получают transit;
уверенность других ролей ограничена. Это следует опубликованной семантике A.
Проверены Timestamp/NaT и 25 тестов scoring. Теперь также выполнены три
интеграционных теста на фактическом выходе A для всех 2 248 узлов; все 28 прошли.
Production-код scoring не потребовал исправлений.

Перед каждым изменением проверяем main, нашу ветку, ветки/файлы коллег и их
контракты. Переиспользуем подходящие компоненты; не меняем граф, API, общие
конфиги или чужие тесты. Публикуем только явно перечисленные файлы своей зоны.

## Воспроизведение проверки A → scoring

Проверенные версии: граф A `3651a714`, scoring `roles-v1.2` (код `0763d79`).
Используются load_dataset, build_graph, detect_communities и compute_features
из опубликованной ветки коллеги. В текущую ветку граф включён merge без правок
авторских файлов; отдельный checkout для запуска больше не требуется.
Нужны зависимости A: pandas, PyArrow, NetworkX и SciPy.

Из корня нашей ветки после установки зависимостей (путь до data замените на свой):

```bash
MONEYGRAPH_DATA_DIR=/absolute/path/to/data python3 -B -m unittest discover -s tests/scoring -v
```

Если данные не переданы, интеграционная группа пропускается. Если переменная
задана, отсутствие модуля/зависимости считается ошибкой, а не успешным пропуском.
Три теста проверяют приём полного FeatureTable без изменения исходной таблицы,
сохранение ограничений, роли/очередь/JSON/CSV-записи и независимость scoring от
порядка входных строк. CSV проверяется в памяти, файлы исходных данных не изменяются.

Фактический результат: 28 тестов прошли, 2 248 узлов, 105 кластеров; load→scored
0.827 с и отдельно scoring 0.104 с. Среда: Python 3.12.14, pandas 2.2.3,
PyArrow 25.0.1, NetworkX 3.7, SciPy 1.17.0. Это прежний замер A → scoring;
теперь отдельно проверены общий CLI с CSV, снимком и API C a749d9c, см. README.
Числа ролей не используются как константы
в тестах — проверяются условия, полнота и согласованность результатов.
