## Запуск блока A

Из корня checkout с установленными зависимостями:

```python
from moneygraph.io.load import load_dataset
from moneygraph.analytics.graph import build_graph
from moneygraph.analytics.communities import detect_communities
from moneygraph.analytics.features import compute_features

dataset = load_dataset("data", period_start="2026-07-01", period_end="2026-07-31")
graph = build_graph(dataset.nodes, dataset.edges, max_depth=dataset.quality["max_depth"])
assignment, cluster_stats, community_meta = detect_communities(graph, resolution=1.0, seed=42)
features, feature_meta = compute_features(
    graph, dataset.transactions, assignment,
    period_end=dataset.quality["period_end"], max_hops=4, betweenness_k=128, seed=42,
)
```

Эти функции выполняют только блок A; это не CLI полного продукта. B сохраняет quality и metadata в снимок, добавляет роли, гипотезы, приоритеты и экспорты.

## Контракт A → B

| Объект | Содержание |
|---|---|
| `LoadedTables` | nodes, edges, transactions как DataFrame; quality как dict |
| nodes | gid:int64, depth:int, is_seed:bool; отсортированы по gid |
| edges | src/dst:int64, sum_kzt исходное, sum_minor:int, n_tx:int, depth:int; сортировка src/dst |
| transactions | Все исходные строки, date:datetime64, sum_minor:int, tx_ref:int; исходный порядок |
| graph | NetworkX DiGraph; узлы gid/depth/is_seed, рёбра sum_minor/n_tx/depth |
| assignment | DataFrame gid:int64, cluster_id:int; одна строка на узел |
| cluster_stats | cluster_id, n_nodes, n_seed, sum_minor_internal; без ролей и текстовых гипотез |
| community_meta | Метод, resolution, seed, версия NetworkX, внутренний/межкластерный/общий оборот |
| features | Одна строка на каждый входной gid; поля перечислены ниже |
| feature_meta | Режим центральности, k/seed, вес PageRank, BFS-лимит, версия NetworkX, число компонент/изолятов |

Один экземпляр LoadedTables не должен изменяться вызывающим кодом: frozen-контейнер не делает DataFrame неизменяемым. Для преобразований используйте копию.

### Поля features

| Группа | Поля и семантика |
|---|---|
| Идентичность | gid, depth, is_seed, component_id, cluster_id |
| Контрагенты | in_degree, out_degree; уникальные другие узлы, self исключён |
| Потоки | in_minor, out_minor; целые тиыны, self-loop учитывается в обоих потоках |
| Количества | in_tx, out_tx; число переводов, включая self-loop |
| Даты | active_in_days, active_out_days, active_days; last_in_date, last_out_date nullable |
| Центральности | pagerank, betweenness; float, не вероятности правонарушения |
| Seed | reachable_seeds:int; seed_paths:list[list[int]], максимум 3 пути |
| Сообщества | other_neighbor_clusters:int; различные кластеры соседей кроме собственного |
| Отношение | observed_flow_ratio:float/NaN при нулевом входе; flow_ratio_eligible:bool |
| Ограничения | depth_boundary, truncated_by_depth, isolated, month_end_window:bool; observation_flags:list[str] |

`active_days` считает объединение дней входа и выхода. `truncated_by_depth` означает границу и отсутствие любых исходящих рёбер. `depth_boundary` определяется глубиной и сохраняется даже если некоторые исходящие на границе оказались известны.

Для JSON B/C конвертируют gid и деньги в десятичные строки, NaN/NaT в null, даты в ISO. В CSV gid остаётся int64; KZT получается из целых тиынов с двумя десятичными знаками, без промежуточного float. JSON нельзя формировать непосредственным дампом DataFrame со значениями NaN. Для Parquet список маршрутов и флагов поддерживается PyArrow; способ снимка выбирает B.

## Граф и метрики

Сначала добавляются все nodes, затем отсортированные рёбра. Деньги не используются как длины кратчайших путей. PageRank взвешен sum_minor. Betweenness — направленный, невзвешенный, normalized=True, k=min(128,N), seed=42. На маленьком графе k=N даёт точный режим; на большом это оценка. Положительный процентиль для скоринга рассчитывает B.

Каждый seed запускает BFS до 4 рёбер с visited. Соседи отсортированы. Один seed засчитывается для узла один раз, сам себе — никогда, в том числе через цикл. Сохраняется до трёх кратчайших путей от разных seed в порядке их gid. Это не обязательно три глобально кратчайших маршрута среди всех seed. Всего считаются все достижимые seed, независимо от лимита примеров. BFS не проверяет хронологию транзакций и не доказывает прохождение одних и тех же средств.

В ориентированном графе сохраняются self-loop и суммы. В отдельной неориентированной проекции self-loop исключается, встречные направления складываются. Внутри каждой связной компоненты выполняется Louvain resolution=1.0/seed=42; одиночные узлы получают собственный кластер. Составы кластеров сортируются по минимальному gid, затем назначаются ID от 0. Порядок входных строк не меняет результат при фиксированных зависимостях и параметрах.

Внутренний оборот — сумма исходных направленных рёбер внутри группы ровно один раз, включая self-loop. Внутренний плюс межкластерный оборот равен полному.

## Уточнения к архитектуре

1. **Компонентный Louvain меняет масштаб оптимизации.** resolution=1 по каждому компоненту не эквивалентен resolution=1 на полном графе. Реализация следует архитектуре, а не пытается сохранить прежнее число 91. [Документация NetworkX](https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.community.louvain.louvain_communities.html) задаёт нормировку через суммарный вес графа.
2. **Период нужен явно.** Если последняя операция 25 июля, это не означает окончание выгрузки 25 июля. `month_end_window` использует параметр period_end.
3. **PageRank требует SciPy.** Добавить его в зависимости B вместе с остальным стеком; собственный pyproject роль A не создаёт.
4. **Совпадающие операции сохраняются.** Перестановка файла изменяет доказательные tx_ref и хеш, но не бизнес-результаты; это разные уровни детерминизма.

## Проверка устойчивости Louvain

Изменялся только resolution, random seed оставался 42. Baseline **1.0 сохранён**. Метод, данные и версии библиотек одинаковы. ARI сравнивает принадлежность пар узлов к группам с поправкой на случайное совпадение; нумерация cluster_id на него не влияет. Значение 1 означает совпадающие разбиения. Здесь нет истинной разметки: это сравнение конфигураций, не accuracy. [Определение ARI](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.adjusted_rand_score.html).

Для расчёта ARI используется стандартная формула через количества пар в таблице сопряжённости, с целочисленной арифметикой до финального деления. Проверены переименование меток, совпадение, пересекающиеся группы с ARI=-0.5, тривиальные разбиения и несовпадающие наборы узлов.

| resolution | Сообществ | С несколькими seed | Мин. / медиана / P90 / макс. размера | Оборот внутри | ARI к 1.0, все узлы | ARI, крупнейшая компонента |
|---|---:|---:|---|---:|---:|---:|
| 0.8 | 99 | 8 | 1 / 5 / 70.2 / 279 | 90.5870% | 0.941680 | 0.935309 |
| **1.0** | **105** | **8** | **1 / 5 / 57.8 / 272** | **90.0468%** | **1.000000** | **1.000000** |
| 1.2 | 123 | 7 | 1 / 4 / 54.6 / 263 | 89.2583% | 0.883406 | 0.867507 |

P90 — линейно интерполированный 90-й перцентиль размеров сообществ; дробное значение не означает дробное число участников. Крупнейшая компонента содержит 1 877 узлов. На всех трёх конфигурациях покрыты все 2 248 узлов, сумма внутренних и межкластерных оборотов равна 36 589 001 201 тиын.

| resolution | Размер 1 | 2–5 | 6–20 | 21–100 | >100 |
|---|---:|---:|---:|---:|---:|
| 0.8 | 19 | 35 | 23 | 14 | 8 |
| 1.0 | 19 | 37 | 25 | 16 | 8 |
| 1.2 | 25 | 46 | 27 | 17 | 8 |

Это количество сообществ в каждом диапазоне, не количество узлов. Singleton-сообщество не обязательно изолят: при resolution=1.2 одиночных сообществ 25, но изолированных узлов графа по-прежнему 19.

Внутренние / межкластерные обороты в тиынах:

- 0.8: 33 144 862 797 / 3 444 138 404;
- 1.0: 32 947 210 997 / 3 641 790 204;
- 1.2: 32 658 730 903 / 3 930 270 298.

**Интерпретация:** ARI показывает близость разбиений, но границы отдельных групп чувствительны к разрешению. Полностью неизменный состав собственной группы сохранили 897 узлов при 0.8 и 1 109 при 1.2 относительно baseline. Это строгая мера: изменение одного соседа меняет состав группы для всех её участников. Высокий ARI не позволяет обещать неизменность каждой карточки или организованную природу групп. Изменение random seed и устойчивость top-20 этим экспериментом не проверялись.

## Воспроизведение отчёта и локальные сценарии демо

Из корня нашей ветки с установленными зависимостями:

```bash
python tests/graph/review_graph.py --data ./data --out ../moneygraph-review-local
```

Это вспомогательная проверка роли A, не второй продуктовый CLI. Команда создаёт **вне репозитория**:

- `stability.json`: результаты всех трёх конфигураций, полный отсортированный список размеров, ARI, суммы, хеши входов и исходников, версии и параметры;
- `demo-scenarios.local.json`: выбранные gid, ожидаемые признаки, примеры направленных путей, межкластерные связи и шаги демонстрации.

Конкретные gid не захардкожены: выбор детерминирован по признакам с разрешением равенств через gid. Результаты не отправляются в сеть. Для повторного запуска выбрать новый каталог: проверка отказывается перезаписывать существующие файлы. Локальный JSON с gid и исходные транзакции в Git не добавлять.

| Сценарий | Как выбирается | Что проверяем на экране |
|---|---|---|
| Изолированный seed | Минимальный gid среди изолированных seed | Узел находится поиском, потоки нулевые, соседей нет; это не оценка безопасности |
| Четвёртое колено, depth=4 | Максимум плательщиков, затем входящей суммы среди граничных узлов без исходящих с сохранённым путём из пяти узлов | Четыре направленных ребра и предупреждение об обрыве; отсутствие выхода не доказательство удержания |
| Сходимость seed-веток | Максимум reachable_seeds с двумя или более примерами маршрутов | Разные seed достигают узла; число примеров ограничено тремя, общий счётчик не ограничен |
| Сбор денег | Не seed и не граница; минимум три плательщика, их минимум вдвое больше получателей; максимум in_degree, затем суммы | Входящие стрелки и число разных плательщиков; это структурный пример, роль присваивает B |
| Распределение денег | Не seed и не граница; минимум три получателя, их минимум вдвое больше плательщиков; максимум out_degree, затем суммы | Исходящие стрелки и число разных получателей, отдельно число операций; роль присваивает B |

На выданном наборе все пять сценариев найдены, пути и связи проверены. Среди отобранных примеров есть узел, достижимый от 11 разных seed. Это структурная характеристика, не доказательство роли координатора. Для каждого локального примера JSON содержит флаги, включая is_seed, чтобы не скрывать неполноту входа. Поля incoming_edges/outgoing_edges содержат до пяти реальных направленных связей каждого вида для демонстрации; это примеры, а не вся окрестность. При нуле контрагентов в знаменателе критериев отбора используется max(1, degree). Критерии выбирают наглядные примеры и не заменяют правила скоринга B.

Короткое объяснение для защиты:

- in_degree/out_degree — число разных плательщиков/получателей, in_tx/out_tx — число операций. Повторные операции сохраняются.
- reachable_seeds считает исходных клиентов, достигающих узла по направлению переводов за максимум четыре шага. seed_paths показывает до трёх кратчайших примеров; последовательность переводов по времени не доказана.
- PageRank характеризует положение в сети с весами сумм; betweenness — посредничество на направленных кратчайших путях, с выборкой до 128 источников. Ни один показатель отдельно не доказывает нарушение.
- При resolution 0.8/1.0/1.2 получены 99/105/123 сообщества. ARI относительно 1.0 — примерно 0.942/1.000/0.883: разбиение чувствительно к масштабу, поэтому сообщества служат гипотезами для проверки. Это проверка resolution при seed=42, не проверка устойчивости к случайному seed или к изменению данных.

После обновления helper повторить запуск в новом каталоге, например `--out ../moneygraph-defense-local`. Тимлид проверяет эти gid в итоговом снимке и интерфейсе; успешный локальный отчёт A сам по себе не подтверждает работу UI.

## Дневная активность клиента — ветка codex/daily-activity

Новый модуль роли A: `moneygraph/analytics/temporal.py`. Нужен для ответа на вопрос
«Когда клиент получал и отправлял деньги?». Скоринг, роли и существующие признаки
не меняются. Новых зависимостей нет. Модуль и локальный HTML-просмотр готовы;
endpoint и график внутри основного приложения подключает C в своих файлах.

### Контракт

```python
from moneygraph.analytics.temporal import daily_activity

result = daily_activity(
    node,                  # существующий клиент из того же проверенного снимка
    transactions,          # ВСЕ записи клиента или полный журнал, не HTTP-страница
    period_start="2026-07-01",
    period_end="2026-07-31",
    max_depth=4,
)
```

`node` — словарь с gid; is_seed, depth и списки warnings/observation_flags
сохраняют ограничения наблюдения. Записи операций содержат src, dst, date,
sum_minor. Принимаются целые ID/тиыны загрузчика A или их десятичные строки API C.
DataFrame передавать через `.to_dict("records")`. Поддерживаются ISO-даты,
Python date и datetime/Timestamp в полночь без часового пояса. Float-деньги/ID,
неположительные суммы, время внутри дня и операции клиента вне периода отклоняются.

Возвращается JSON-совместимый словарь:

| Поле | Смысл |
|---|---|
| schema_version | `daily-activity.v1` |
| gid | Строковый ID клиента, без потери int64 в JavaScript |
| period | start/end, обе даты включены |
| available | История предоставлена; `None` на входе означает недоступность |
| currency / scale / date_precision | KZT / 2 / day |
| days | Все календарные дни по возрастанию, включая нулевые |
| days[].in_minor / out_minor | Строки целых тиынов поступлений/отправлений |
| days[].net_minor | Разница наблюдаемых поступлений и отправлений; **не остаток счёта** |
| days[].in_tx / out_tx | Числа входящих/исходящих операций |
| days[].self_tx | Число переводов самому себе |
| days[].n_transactions | Число строк операций, self-transfer считается один раз |
| totals | Те же суммы/счётчики за период плюс active_days |
| warnings | Ограничения выборки и клиента |

Пустой список означает известную пустую историю: получаем нулевые дни.
`transactions=None` даёт available=false, days=[], totals=null. Нельзя заменять
недоступные операции пустым списком. Неизвестный gid должен дать 404 в API до
вызова функции; модуль доверяет переданному объекту существующего клиента.

Повторные операции не удаляются. Перевод самому себе входит в оба направления,
но имеет нулевой net_minor и одну строку n_transactions. Поэтому
`n_transactions = in_tx + out_tx - self_tx`. Денежные суммы складываются как
Python int; JavaScript получает строки. Итоги не зависят от порядка записей.

### Подключение в зоне C

В проверенном C `53d611e` уже есть полный индекс `service.transactions[gid]`.
Использовать его, а не `node_transactions(...)["items"]`, где действует пагинация.
Пример адаптера для endpoint (сам endpoint в этой ветке **не добавлен**):

```python
node = service.node(gid)  # тот же механизм проверки существования, что у карточки
period = service.manifest["period"]
rows = service.transactions.get(gid, []) if service.transactions_available else None
data = daily_activity(node, rows, period_start=period["start"], period_end=period["end"])
return service.envelope(data)  # сохраняет run_id исходного снимка
```

Если глубина расчёта не равна четырём, передать max_depth из конфигурации снимка.
Предлагаемый маршрут после согласования: GET `/api/v1/runs/{run_id}/nodes/{gid}/daily-activity`.
Группировка по дням не должна повторять расчёт PageRank или сообществ.

В карточке C: два столбца на день («Поступления», «Отправления»), суммы в KZT,
подсказка с датой/суммами/числом операций, таблица точных значений. Для графических
координат допустимо приближение; точные подписи брать из строк, форматируя через
существующий money/BigInt. Отдельные состояния: загрузка, ошибка, история
недоступна и известные нулевые операции. Период брать из снимка, а не из последней
наблюдаемой операции. Шкала не означает порядок переводов внутри дня.

### Локальная проверка до подключения UI

```bash
python tests/graph/review_daily_activity.py --data ./data --out ../moneygraph-daily-local
```

По умолчанию выбирается клиент с максимальным числом наблюдаемых операций;
при равенстве — минимальный gid. Это наглядный пример, не новый рейтинг риска.
Для конкретного клиента добавить `--gid ID_КЛИЕНТА`. Создаются:

- `daily-activity.local.html`: автономный график и таблица, открываются браузером;
- `daily-activity.local.json`: точные суммы, счётчики, флаги и хеши входных файлов.

Оба файла содержат локальные финансовые данные: не коммитить. Сеть и внешние
сервисы не используются. Для повторного запуска нужен новый --out, существующие
файлы не перезаписываются. Этот helper — проверка A, не замена продуктового CLI B.
