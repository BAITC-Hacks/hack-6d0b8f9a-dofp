# Проверка порогов и влияния caps

23 сентября 2026. Данные: 2 248 узлов, граф A `3651a714`, resolution=1.0,
seed=42, betweenness_k=128, период 2026-07-01…2026-07-31. Правила roles-v1.2.
Использован **настоящий features.parquet общего запуска**, повторно прочитанный
через PyArrow. Пути и списки предупреждений после чтения сохранены.

## Почему в priority используется support

`assignment.support` описывает, насколько наблюдаемое поведение соответствует
прошедшему правилу. `role_score` дополнительно ограничивает уверенность в выбранной
роли: например, две близкие гипотезы дают cap=0.6. Две правдоподобные роли могут
снижать уверенность в ярлыке, сохраняя ценность узла для ручного исследования.
Поэтому текущий priority использует support, а не умножение на role_score.

Это **инженерный выбор цели очереди**, а не доказанное преимущество. Если команда
хочет сначала рассматривать узлы с наиболее определённой ролью, caps следует
учесть и в очереди. Эту цель нужно выбрать явно, не объявляя score вероятностью
преступления. Формулу без решения команды не меняли.

## Прямое сравнение двух очередей

Baseline: `0.35*S + 0.25*support + 0.25*B + 0.15*V`.
Вариант: заменено только `support` на `min(support, role_score)`.
Для peripheral это сохраняет 0 поддержки: условный fallback role_score=0.2
не превращается в положительный сигнал. Остальные факторы и правила не менялись.

| Показатель | Результат |
|---|---|
| Узлов, у которых cap снижает support | 215 из 2 248 |
| Лидеров baseline top-20 с действующим cap | 19 из 20 |
| Причина caps у этих 19 | Конкурирующие роли (`ambiguous_roles`) |
| Состав baseline top-20 по ролям | 15 distributor, 5 coordinator |
| Узлов глубины 4 в baseline top-20 | 0 |
| Общие участники двух top-20 | **7 из 20** |
| Лидеров baseline, сменивших позицию | 20 из 20 |
| Максимальное смещение позиции среди прежних лидеров | 23 места |
| Максимальное снижение priority по всем узлам | 0.125 |
| Среднее снижение priority | 0.004689 |

**Вывод для тимлида:** очередь существенно зависит от выбранной трактовки
неопределённости роли. Стабильность отдельных порогов ниже не снимает этот вопрос.
В UI уже передаются отдельные role_score/priority_score, полные caps, конкурирующие
кандидаты и четыре числовых вклада. Интеграционный тест проверяет, что API сохраняет
caps и ограничения. Конкретные gid и финансовые строки в отчёт не включены.

## Изменение одного порога на ±20%

Признаки графа зафиксированы; это не проверка устойчивости Louvain (её делает A).
Целочисленные пороги округляются вверх, доли ограничиваются единицей;
варианты, не изменившие порог, пропускаются. В каждом из 16 вариантов состав
top-20 сохраняется полностью, но роли меняются:

Сохранение состава не означает сохранение всех позиций, истинность назначенных
ролей или точность AML-классификации. Размеченной истины нет; тест не измеряет
precision/recall и не проверяет одновременное изменение нескольких порогов.

## Как воспроизвести

Сначала общий CLI создаёт снимок и печатает его каталог. Из корня проекта:

```bash
PYTHONPATH=. python -B tests/scoring/validate_features.py out/runs/RUN_ID/features.parquet --period-end 2026-07-31 --sensitivity --compare-caps
```

Заменить RUN_ID на напечатанный идентификатор. PowerShell: перед командой
`$env:PYTHONPATH = "."`, затем команда начинается с `python`.
Вывод — только агрегированный JSON; production priority и файлы снимка не меняются.
