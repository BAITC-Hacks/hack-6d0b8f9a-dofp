# API и интерфейс — роль C

Состояние: реализованы локальный API, интерфейс расследования, загрузка Parquet через браузер и понятный Excel-отчёт. Расчёт ролей и приоритетов остаётся ответственностью роли B; признаки и сообщества — роли A. Демонстрационные данные используются только при явном `--demo`.

Приёмка объединённой версии 23 сентября 2026: A `dfc1ed0`, B `81c5e8d` и C объединены без конфликтов. **120 тестов и 36 подслучаев прошли без пропусков**, включая настоящий HTTP-процесс --serve, все 2 248 карточек, повреждение снимка и побайтовую сверку трёх CSV. Чистые Python 3.12 venv и frontend install по lock-файлу проверены; pip check, TypeScript и production build успешны. Одна сторонняя deprecation warning Starlette/httpx остаётся.

Полный CLI занял 8,563 с в чистой Windows-среде, установленный wheel вне исходников — 6,315 с; run_id совпал. Установка и открытие браузера не входят в эти замеры. Это измерения нашей среды, не гарантия машины жюри и не оценка качества AML-гипотез.

## Загрузка и понятный отчёт через интерфейс

Запустить приложение без готового расчёта:

```bash
python -m moneygraph.api --empty --port 8000
```

В интерфейсе нажать **«Новые данные»**, выбрать одновременно `nodes.parquet`, `edges.parquet` и `transactions.parquet` одного набора, указать период, охватывающий все переводы, и нажать **«Загрузить и рассчитать»**. Показываются загрузка, проверка и расчёт; после успеха открывается новый результат. CSV/XLSX на вход не поддерживаются. В раскрываемой подсказке указана схема Parquet.

Импорт вызывает существующий `run_pipeline` роли B и проверки роли A. До успешной проверки файлов и нового снимка предыдущий результат остаётся активным; неудачная загрузка его не заменяет. Суммы, роли и правила не пересчитываются отдельной логикой UI. Переводы за пределами выбранного периода отклоняются: даты здесь задают контракт набора, а не фильтруют произвольный общий файл.

Файлы обрабатываются на локальном компьютере. Лимиты MVP: 40 МиБ на файл, 10 000 строк клиентов, 50 000 строк связей, 200 000 строк переводов. Один расчёт одновременно. Временные загрузки удаляются после завершения или ошибки; незавершённая загрузка освобождается при новой попытке через 15 минут. Завершённые снимки сохраняются в `out/imports/runs/RUN_ID` относительно рабочей папки, которая не попадает в Git. Они остаются на диске после остановки сервера; для повторного открытия передать нужный каталог через `--snapshot`. Это локальный однопользовательский режим, сервер слушает loopback.

Карточки показывают обычными словами количество отправителей и получателей и смысл предполагаемой роли. В группах отдельно подписаны переводы внутри и между группами. Для изолированного клиента `0 ₸` явно означает отсутствие наблюдаемых переводов, а не нулевой баланс. Исходные доказательства и правило доступны в «Подробностях расчёта». Нижний декоративный значок AML удалён.

**«Экспорт результатов» → «Открыть в Excel — рекомендуется»** выдаёт `moneygraph.xlsx`: русские заголовки, объяснения, четыре листа, номера клиентов в текстовых ячейках без потери последних цифр. Это дополнительное представление результатов. Три CSV по ТЗ выдаются отдельными ссылками побайтово без изменения; открытие такого UTF-8 CSV двойным щелчком зависит от версии/настроек Excel. [Microsoft объясняет особенности открытия UTF-8 CSV](https://support.microsoft.com/en-us/excel/opening-csv-utf-8-files-correctly-in-excel).

API: `POST /api/v1/imports` (period_start, period_end), `PUT /api/v1/imports/{id}/files/{name}` (байты файла), `POST /api/v1/imports/{id}/run`, `GET /api/v1/imports/{id}`. Изменяющие запросы требуют локального Host, заголовка `X-Moneygraph-Client: local-ui` и совпадения Origin, если он передан; CORS не включён. XLSX: `GET /api/v1/runs/{run_id}/reports/moneygraph.xlsx`.

Проверки дополнены настоящим pipeline импорта, переключением текущего снимка, сохранением старого при ошибке периода, лимитами загрузки, блокировкой чужого Origin/Host и сохранением Unicode/18-значных номеров в XLSX. Зависимости ядра и схемы трёх CSV не изменены.

## Подключение результата текущего pipeline B

Из корня объединённого checkout, после создания и активации Python 3.12 venv:

```bash
python -m pip install '.[serve,dev]'
python -m moneygraph run --data ./data --out ./out --serve
```

Открыть http://127.0.0.1:8000, при занятом порте добавить --port 8002. Данные лежат только локально. Node для запуска не нужен: frontend/dist включён в Git. Флаг --serve уже реализован B и проверен C.

Повторное открытие готового результата без пересчёта: `python -m moneygraph.api --snapshot ./out/runs/RUN_ID`. Подставить напечатанный run_id. Снимок сам содержит транзакции и граф. Не передавайте out/current.json как JSON-снимок: это указатель, API закрепляет конкретный каталог запуска.

Wheel содержит Python-пакет, но не frontend/dist. При запуске установленного пакета вне checkout передать общему CLI `--static-dir ABSOLUTE_PATH/frontend/dist`. Этот режим тоже проверен. Ошибочный явный путь к frontend останавливает запуск; при отсутствии сборки в режиме API-only корневой маршрут отвечает 503 с понятной причиной. Канонический запуск для защиты — из корня клона.

Для проверки реального снимка задать MONEYGRAPH_SNAPSHOT_DIR абсолютным путём к out/runs/RUN_ID и запустить pytest tests/api. Без этой переменной файловая интеграционная проверка пропускается, остальные API-тесты выполняются.

Полная приёмка PowerShell (после генерации снимка):

```powershell
$env:PYTHONUTF8 = '1'
$env:MONEYGRAPH_DATA_DIR = (Resolve-Path ./data).Path
$env:MONEYGRAPH_API_TESTS = '1'
$env:MONEYGRAPH_SNAPSHOT_DIR = (Resolve-Path ./out/runs/RUN_ID).Path
python -m pytest -q
```

## Решение тимлида об очереди и сценарий защиты

Сохраняем формулу B: очередь предназначена для исследования сильных структурных сигналов, а не ранжирования уверенности в конкретной роли. Ограничение role_score не уменьшает автоматически priority_score. В сравнении B замена support на ограниченную оценку оставляет 7 из 20 лидеров; это существенный выбор методики, а не косметическая настройка. UI теперь показывает причины caps и объясняет, почему высокий приоритет совместим с неоднозначной ролью. Формула расчёта не изменена.

В браузере пройдены все пять сценариев из `tests/graph/review_graph.py`: изолированный seed (нулевые потоки и пустые операции), граница depth=4 (предупреждение и пути), сходимость 11 seed (три примера путей), сбор (13 плательщиков / 1 получатель), распределение (2 / 116). Карточки согласуются с итоговым снимком; проверены окрестности, ограничения роли и загрузка CSV. Ошибок JavaScript нет.

Пятиминутная демонстрация: 30 с — сводка и неполнота выборки; 60 с — очередь, основания и caps; 90 с — сбор/распределение/пути; 60 с — граница и изолят; 60 с — три CSV одного run_id, время запуска и устойчивость сообществ. Gid сценариев генерируются локально, не добавляются в Git. Команда: `python tests/graph/review_graph.py --data ./data --out ../defense-local` (выбрать новый каталог).

## Целостность снимка

Для moneygraph.snapshot.v1 API проверяет run_id по каноническому identity, точный набор восьми артефактов и SHA-256 каждого файла. Файлы читаются один раз: проверяются, разбираются и экспортируются одни и те же закреплённые байты. Проверяются согласованность операций с агрегированными рёбрами и внутренние суммы кластеров. Несоответствие останавливает загрузку, успешный пустой экран не выдаётся. Хеши обнаруживают повреждение и рассогласование; они не являются цифровой подписью или доказательством доверенного происхождения.

Старый формат 1.x для синтетических/внутренних mapping-снимков сохранён; для него manifest-хеши не обязательны. Не следует считать его эквивалентным проверенному файловому контракту B. Даты принимаются как календарный день; ненулевое время не отбрасывается молча. Денежные суммы операций положительные, а счётчики не округляются из float/bool.

Решения опираются на первичные рекомендации: [Google Cloud — проверять контрольные суммы полученных байтов](https://docs.cloud.google.com/storage/docs/data-validation), [Microsoft Azure — явные контракты API, валидация и ограничение выборок](https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-design). Применён соответствующий принцип, а не заявлена эквивалентность инфраструктуре этих компаний.

## Быстрый запуск

Из корня репозитория, Python 3.12:

```bash
python -m venv .venv
# Windows PowerShell: .venv\Scripts\Activate.ps1
# Linux/macOS: source .venv/bin/activate
python -m pip install '.[serve]'
python -m moneygraph.api --demo
```

Открыть http://127.0.0.1:8000. Собранный frontend находится в `frontend/dist`; Node для такого запуска не нужен. Сервер слушает только loopback. Если порт занят: `--port 8001`.

Для настоящих результатов:

```bash
python -m moneygraph.api --snapshot ./out/RUN_ID --data ./data
```

`--snapshot` указывает на завершённый каталог конкретного запуска, не на каталог со множеством запусков. Можно передать один JSON с форматом снимка ниже. `--data` необязателен, если связи, метаданные узлов и транзакции уже находятся в снимке. API не пересчитывает роли, оценки или кластеризацию. Отсутствие транзакций отображается как «не подключены», а не как отсутствие активности.

## Подключение к общему CLI роли B

```python
from moneygraph.api import create_app
import uvicorn

app = create_app(snapshot)  # mapping, dataclass, Pydantic model или Path
uvicorn.run(app, host="127.0.0.1", port=8000)

# Вариант из файлов:
app = create_app("out/RUN_ID", data_dir="data")
```

`snapshot` должен соответствовать описанному формату: автоматического угадывания произвольных полей общего DTO нет. `QueryService` доступен из `moneygraph.api.service`. Преобразование общего `AnalysisSnapshot` выполняется на границе интеграции. Нельзя импортировать API-модели в ядро графовых расчётов.

Общий CLI `python -m moneygraph run ... --serve` реализован ролью B и включён в интеграцию; C предоставляет `python -m moneygraph.api` и `create_app`. Расчётные файлы коллег сохранены без изменений.

## Каталог завершённого запуска

```text
out/RUN_ID/
  manifest.json           # обязательно
  nodes_roles.csv         # обязательно, схема ТЗ
  clusters.csv            # обязательно, схема ТЗ
  top_nodes.csv           # обязательно, схема ТЗ
  graph.json              # обязательно, если нет --data/edges.parquet
  features.parquet        # дополнительные признаки
  explanations.jsonl      # подробные объяснения, строка на gid
  transactions.parquet    # если отсутствует, используется --data/transactions.parquet
  quality.json            # необязательно, сведения о качестве
```

Метаданные `depth` и `is_seed` должны быть доступны через features, nodes_roles, узлы graph.json или `--data/nodes.parquet`. При противоречии метаданных и агрегатов кластеров загрузка завершается ошибкой, а не выдаёт фиктивные числа. Исходные CSV читаются в память при запуске и далее отдаются без изменений; изменение файлов под работающим сервером не смешивает версии. Новый расчёт можно загрузить через интерфейс: после полной проверки он становится текущим. API хранит до четырёх открытых расчётов, чтобы запросы по старому run_id не смешивались с новым; готовые каталоги остаются на диске.

Пример `manifest.json`:

```json
{
  "run_id": "run-202607-v1",
  "schema_version": "1.0",
  "rules_version": "rules.v1",
  "period": {"start": "2026-07-01", "end": "2026-07-31"},
  "demo": false,
  "warnings": []
}
```

run_id: 1–128 символов `[A-Za-z0-9._-]`, первый символ буква или цифра. Поддерживается major-версия схемы 1.

`graph.json`:

```json
{
  "nodes": [{"gid": "123", "depth": 1, "is_seed": false}],
  "edges": [{"src": "123", "dst": "456", "sum_minor": "25000000", "n_tx": 3}]
}
```

Это фрагмент схемы, не самостоятельный полный снимок: оба конца каждого ребра должны существовать в nodes_roles. Поддерживаются также ключи source/target и Cytoscape-обёртка `elements` / `data`. Для сумм допустим sum_kzt вместо sum_minor; дробный тиын отклоняется, незначительный шум float после суммирования допускается в пределах 0.000001 тиына.

## Формат снимка в памяти / JSON

```python
snapshot = {
    "manifest": {...},
    "nodes": [...],
    "edges": [...],
    "clusters": [...],
    "top_nodes": [...],     # можно не передавать: API сортирует уже готовые priority_score
    "transactions": [...],  # необязательно
    "quality": {...},       # необязательно
}
```

Сортировка готовых оценок не является расчётом скоринга. Если top_nodes передан, проверяются уникальность gid, последовательность рангов, убывание оценок и совпадение ролей/оценок с nodes. На предоставленном датасете ответственность за ≥20 строк и все 2 248 узлов остаётся у пайплайна; API допускает малые синтетические тестовые снимки.

Узел:

```json
{
  "gid": "123",
  "role": "consolidator",
  "role_score": 0.6,
  "priority_score": 0.72,
  "cluster_id": 1,
  "evidence": "Признаки консолидации: 7 плательщиков. Входящие потоки видны не полностью.",
  "depth": 2,
  "is_seed": false,
  "metrics": {
    "in_deg": 7, "out_deg": 2,
    "in_minor": "125000000", "out_minor": "70000000",
    "in_tx": 12, "out_tx": 5, "reachable_seeds": 3
  },
  "warnings": ["sampling_threshold"],
  "rule_id": "consolidator.v1",
  "contributions": [
    {"key": "seed_context", "label": "Связи с исходными узлами", "value": 0.30},
    {"key": "role_support", "label": "Признаки роли", "value": 0.20},
    {"key": "network_position", "label": "Положение в сети", "value": 0.15},
    {"key": "volume", "label": "Объём переводов", "value": 0.07}
  ],
  "paths": [["100", "110", "123"]]
}
```

Поля gid/role/role_score/priority_score/cluster_id/evidence обязательны; evidence непустое, ≤200 символов. Разрешены ровно шесть ролей из ТЗ. Оценки конечные и в [0,1]. cluster_id — неотрицательное целое. Неизвестные дополнительные поля узла игнорируются, но не добавляют функциональность интерфейсу автоматически.

API также подхватывает плоские столбцы in_deg, out_deg, in_tx, out_tx, pagerank, betweenness, reachable_seeds, active_days, observed_flow_ratio/pass_through, in_minor/out_minor или in_kzt/out_kzt. Для необязательных метрик NaN/Infinity выдаются как null; такой узел не получает выдуманный ноль. Вклады contributions — уже рассчитанные слагаемые итогового priority_score в шкале 0–1, а не веса факторов. UI умножает оценки и вклады на 100 для отображения.

Кластер: cluster_id, n_nodes, n_seed, sum_minor_internal (или sum_kzt_internal), top_gids (массив идентификаторов), hypothesis. Состав и n_seed проверяются по узлам; top_gids должны принадлежать своему кластеру. Каждый узел должен иметь существующий кластер, включая изоляты.

Транзакция: src, dst, date в ISO YYYY-MM-DD, sum_minor (либо sum_kzt), tx_ref. Без tx_ref API присваивает номер исходной строки. Совпадающие транзакции сохраняются. Ссылки на строки имеют смысл в пределах конкретного run_id/исходного файла.

## JSON и денежные значения

- gid/src/dst всегда строки. Входной int64 допускается, float-идентификатор отклоняется.
- Деньги передаются строками целых тиынов: `"25000000"` = 250 000 KZT. UI форматирует их через BigInt.
- CSV сохраняет схему организаторов с gid как десятичным целым и суммами в KZT.
- Все успешные аналитические ответы: `{schema_version, run_id, data, warnings}`.
- Неподключённый снимок → 503, отсутствующий run/gid → 404, неверные параметры → 422.
- API обслуживает только один неизменяемый run_id за запуск. Никакого неявного переключения на новый результат.

## Эндпоинты

| GET | Описание |
|---|---|
| /health | Готовность и run_id; 503 без снимка |
| /api/v1/runs/current | Manifest, период, статистика, качество |
| /api/v1/runs/{run_id}/nodes | Очередь; role, cluster_id, seed_only, q, limit=50, offset=0 |
| /api/v1/runs/{run_id}/nodes/{gid} | Карточка и исходный ранг |
| /api/v1/runs/{run_id}/graph | gid, hops=1, cluster_id, limit=250 |
| /api/v1/runs/{run_id}/clusters | Список кластеров |
| /api/v1/runs/{run_id}/nodes/{gid}/transactions | limit=50, offset=0, available |
| /api/v1/runs/{run_id}/exports/{name} | Только nodes_roles.csv, clusters.csv, top_nodes.csv |
| /openapi.json | Машиночитаемое описание API |

Окрестность раскрывает входящих и исходящих соседей, но сохраняет направления рёбер. hops=0..2; limit=1..500. При превышении лимита ответ содержит truncated, hidden_nodes, hidden_edges и полные размеры выбранной области. API не перечисляет все простые пути. Фильтры UI меняют только представление; выгрузки и оценки относятся к полному снимку.

## Интерфейс

- Очередь по готовому приоритету, фильтры ролей и seed, пагинация.
- Поиск точного gid по всему снимку, независимо от текущей страницы очереди.
- Граф: стрелки, роли/цвета сообществ, маркеры seed и depth=4, масштаб, перемещение, окрестность 1–2 шага.
- Карточка: роль, поддержка, приоритет, факты, вклады, ограничения и структурные маршруты.
- Переводы: пагинация, суммы, направление, переход к контрагенту; точность времени — день.
- Список сообществ с переходом на граф; экспорт трёх CSV того же run_id.
- Явные состояния отсутствия снимка/транзакций, ошибки загрузки и пустых фильтров.
- Демо всегда имеет баннер и метку в диалоге экспорта. Нет автоматического перехода с настоящих данных на демо.
- Интерфейс не отправляет данные во внешние сервисы. JS/CSS и системные шрифты локальные; runtime не использует CDN.

На узком экране карточка располагается ниже графа. Основной режим — рабочее место на ноутбуке.

## Разработка frontend

Node ≥20.19 или ≥22.12, pnpm 11:

```bash
cd frontend
pnpm install --frozen-lockfile
pnpm dev
```

API отдельно запущен на 127.0.0.1:8000, Vite проксирует /api и /health. Для выпуска:

```bash
pnpm exec prettier --check src index.html package.json tsconfig.json vite.config.ts
pnpm build
```

Сохранять pnpm-lock.yaml и свежий frontend/dist вместе с изменением исходников. В pnpm-workspace.yaml разрешён только необходимый сборочный скрипт esbuild. node_modules не коммитится.

```bash
python -m pip install pytest httpx
```

Тесты покрывают согласованность снимка, int64, пагинацию, фильтры, лимиты, направления рёбер, изолированный узел, повторные транзакции, отсутствие транзакций, неизменяемость экспорта, ошибки схемы и нечисловые метрики. ## Передача команде

### Совместимость с уже опубликованным кодом

Проверены ветки A `codex/data-graph` (3651a71) и B `codex/scoring-rules` (f86a15f). Адаптер API поддерживает их реальные поля:

- `in_degree/out_degree` → метрики `in_deg/out_deg`;
- `seed_paths` → `paths`, включая list-колонки, прочитанные PyArrow как numpy-массивы;
- `observation_flags` и `assignment.limitations` → предупреждения карточки;
- `ScoredNode.explanation_record()` с вложенными features/assignment и словарём contributions;
- дополнительные принятые кандидаты → alternatives; полные условия, факторы, policy и caps → rule_details.

В explanations.jsonl допускается точный результат `explanation_record()`, даже без gid верхнего уровня: используется features.gid. Алгоритмы A/B не изменялись.

Локальный проверочный прогон выданных данных через A → B → API: 2 248 узлов, 3 119 рёбер, 81 seed, 105 сообществ, оборот 36 589 001 201 тиын; карточки первых трёх узлов, их окрестности/транзакции и три экспорта доступны. Прогон занял около 4,6 с в текущей Windows-среде. Это проверка совместимости, не готовый общий CLI и не проверка на машине жюри. Временный тестовый адаптер использовал явно обозначенные заглушки гипотез кластеров и не добавлен в продукт.

Указанный выше предварительный smoke-прогон относится к прежнему B. Актуальная объединённая приёмка B `81c5e8d` с --serve описана в начале документа. Роль C предоставляет адаптер и проверенный create_app; CLI и зависимости включены из ветки B без изменений.

1. Роль A передаёт метаданные и признаки со стабильными gid, а также граф и сообщества.
2. Роль B формирует полный снимок по контракту, создаёт все три CSV и вызывает create_app после успешной публикации.
3. Роль C проверяет один реальный снимок, согласует отклонения формата через адаптер, не меняя расчётные алгоритмы.

Зоны этой ветки: moneygraph/api/, frontend/, tests/api/, docs/ui.md. Общие DTO и зависимости в корне меняет роль B после согласования.
