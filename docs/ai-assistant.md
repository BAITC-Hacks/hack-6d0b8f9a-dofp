# AI-помощник AML-аналитика

Модуль превращает факты готового расчёта в краткую записку на русском языке.
Это объяснение существующих правил и поддержка расследования, не обученный
детектор отмывания денег. Соответствие обязательным AI-требованиям хакатона
тимлид проверяет отдельно по ТЗ.

## Контракт для C

```python
from pathlib import Path
from moneygraph.ai import SnapshotContextBuilder, explain_client, AIUnavailable

# Один раз при подключении завершённого расчёта. Не передавать out/current.json.
facts = SnapshotContextBuilder(Path("out/runs/RUN_ID"))
assert facts.run_id == query_service.run_id

# По запросу карточки: gid берётся из проверенного маршрута backend.
context = facts.for_client(gid)
explanation = explain_client(context)
```

`SnapshotContextBuilder` читает и проверяет хеши байтов всех восьми артефактов
одного native-снимка `moneygraph.snapshot.v1`. Он хранит необходимые записи в
памяти. Замена файлов после загрузки не меняет контекст. Неполный снимок,
несогласованные роли/оценки/признаки или неизвестные ограничения отклоняются.
Текстовые `evidence` и `hypothesis` не пересылаются: берём структурированные
условия правил. Это исключает случайную передачу ID, встроенных в произвольный
текст. Подмена их нулями или придумывание недостающих значений запрещены.

Публичная функция синхронная. Endpoint должен быть обычным `def`, чтобы FastAPI
выполнил его в пуле потоков, либо использовать `run_in_threadpool`. На event loop
вызов не выполнять. Построение адаптера не должно быть обязательным условием
старта обычного API: если AI выключен или его контекст нельзя загрузить, основная
карточка продолжает работать. При смене снимка создаётся новый адаптер.
В обновлённом C `5c99d95` есть импорт и несколько сохранённых расчётов: выбирать
адаптер по `run_id` запроса, как C выбирает QueryService из `runs`. Нельзя брать
текущий снимок из `app.state`, если запрос относится к старому открытому расчёту.

Предлагаемый маршрут: `POST /api/v1/runs/{run_id}/nodes/{gid}/ai-explanation`.
Тело запроса пустое. Модель, URL провайдера, prompt и факты клиент не задаёт.
Проверить совпадение `run_id` с загруженным расчётом и существование `gid`.
Маршрут зарегистрировать **до** catch-all `/api/{unmatched:path}` и mount `/`;
иначе текущий API C перехватит запрос.
Для этого POST C должен применить уже используемые при импорте проверки
локального Host, совпадения Origin и заголовка `X-Moneygraph-Client: local-ui`.
Не оставлять платный внешний вызов доступным произвольному стороннему сайту.

Успех: вернуть обычный envelope C с `run_id` и `data=explanation`.
Ошибка `AIUnavailable`: вернуть 503 и безопасные `error.code`, `str(error)`;
для `busy` / `rate_limited` можно использовать 429. Ошибка контекста
`InvalidContext`: 503 без деталей исходных данных; неизвестный клиент — 404.
Не отправлять traceback или ответ провайдера в браузер.

На успешном результате установить `Cache-Control: no-store` для HTTP-ответа.
Это не отменяет ограниченный кэш модуля в памяти backend. При публикации сервиса
за пределами loopback C должен применить те же контроль доступа и лимиты запросов,
что защищают финансовые карточки; лимит параллельности модуля — не авторизация.

## Формат ответа

Все пять разделов — массивы объектов, а не произвольная Markdown-строка:

| Поле | Содержимое |
|---|---|
| `summary` | 2–3 объекта `{text, fact_ids}` — наблюдения |
| `reasons` | 2–5 объектов `{text, fact_ids}` — роль и приоритет |
| `alternative_hypotheses` | 1–2 объекта `{text, fact_ids, status: "hypothesis"}` |
| `next_checks` | 2–3 объекта `{text, fact_ids, action, availability}` |
| `limitations` | `{text, fact_ids, code}` для каждого обязательного ограничения |
| `facts` | Исходные факты `{id, key, label, value, source}` |
| `metadata` | Снимок, хеш контекста, провайдер, модель, версии инструкций, кэш |

`availability` имеет только `in_product` или `request_data`.
У каждого утверждения, включая summary, есть ссылки. `source` обозначает
артефакт/поле либо ограничение аналитического контракта. Суммы — точные строки
KZT из целых тиынов. Оценки показываются в шкале 0–100 с двумя знаками, без
интерпретации как вероятности. Для отсутствующего значения используется `null`.

В UI рядом с текстом показать кнопки F1, F2…; по нажатию — исходный `label` и
`value` из `facts`, а не ещё один пересказ модели. JSON отрисовывать обычным
текстом React, не через `dangerouslySetInnerHTML` и не как исполняемый Markdown.
В ограничениях должны оставаться все обязательные пункты; их можно свернуть
визуально, но не удалять из ответа или подменять общей фразой.

Клиент карточки всегда называется `Клиент_A`; остальные участники выбранных
путей — `Клиент_B` и далее. `context.alias_map` содержит соответствие псевдонимов
исходным ID **на backend**. Оно не входит в запрос модели или её результат.
C может сопоставить псевдонимы с уже разрешёнными пользователю карточками.
Если пользователь сменил клиента или расчёт во время запроса, UI должен
отбросить устаревший ответ: сверить захваченные при клике `run_id` и `gid` с
текущей карточкой. Записка старого клиента не должна появляться у нового.

## Конфигурация провайдера

### Готовая настройка OpenAI для Freeman

Для объяснения готовых фактов выбран `gpt-6-luna` с `reasoning_effort=low`.
Это начальная конфигурация для приёмки, не измеренное утверждение о качестве
AML-выводов. Модель меняется переменной окружения без изменения кода.
Выбор опирается на официальные страницы
[модели](https://developers.openai.com/api/docs/models/gpt-6-luna) и
[руководство по моделям](https://developers.openai.com/api/docs/guides/latest-model),
проверенные 2026-09-23. Реальная доступность зависит от API-проекта команды.

Профиль использует `https://api.openai.com/v1`, `max_completion_tokens`,
Structured Outputs (`json_schema`, `strict=true`) и `store=false`.
Строгая схема проверяется также нашим backend. Схема не гарантирует истинность
текста. `store=false` не является обещанием отсутствия любых журналов у провайдера.
Документация:
[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs),
[Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create).

После установки `.[serve]` и интеграции этой ветки выполнить в терминале backend:

```bash
export MONEYGRAPH_AI_PROVIDER=openai
export MONEYGRAPH_AI_ENABLED=true
export MONEYGRAPH_AI_ALLOW_EXTERNAL=true
read -r -s -p 'OpenAI API key: ' MONEYGRAPH_AI_API_KEY
export MONEYGRAPH_AI_API_KEY
python -m moneygraph.ai.check --live
```

Ключ вводится после приглашения и не отображается. Программа проверки делает
**один настоящий запрос**, расходующий API-кредиты, с синтетическим `ok=true`;
никакого датасета для него не нужно. Без `--live` проверяются только настройки,
сетевых запросов нет. Это не проверка качества аналитической записки.
После успешной проверки запустить интерфейс в том же терминале; переменные
не переходят автоматически в другой терминал. В текущей ветке AI нет файлов
API/UI C: кнопку должен подключить C в объединённой версии.

Ключ создать в [API-проекте](https://platform.openai.com/api-keys) либо получить
для командного проекта по инструкции организаторов. Ключ от обычной сессии
ChatGPT, cookie или пароль аккаунта здесь не используются.
Альтернатива `MONEYGRAPH_AI_API_KEY` — стандартный `OPENAI_API_KEY`; он читается
только в профиле `openai`. В этом профиле адрес жёстко ограничен
`https://api.openai.com/v1` (допустим стандартный порт 443), поэтому случайная
подмена BASE_URL не отправит автоматически подхваченный ключ другому сервису.

Ошибки `missing_api_key`, `authentication_failed`, `access_denied`,
`model_or_endpoint_unavailable` и `rate_limited` позволяют отличить отсутствие
ключа, неверный ключ, ограничения доступа, неизвестную модель/endpoint и HTTP 429.
HTTP 429 также может означать проблему квоты: детали уточнять в API-кабинете,
тело ответа провайдера в браузер и логи не передаётся. Среда разработки не имеет
API-ключа; live-запрос ещё не выполнен.

### Обновление отдельной папки проверки

Если `moneygraph-demo` содержит API/UI C, а соседняя `moneygraph-ai-check` создана
через `git worktree add --detach`, выполнять из `moneygraph-demo` в том же
терминале, где задан ключ:

```bash
git -C ../moneygraph-ai-check fetch origin &&
git -C ../moneygraph-ai-check merge --ff-only origin/codex/ai-assistant &&
PYTHONPATH="$PWD/../moneygraph-ai-check" .venv/bin/python -m moneygraph.ai.check --live
```

Если обновление не удалось, последующая проверка не запустится. Переустановка
окружения и повторное создание worktree не нужны. Эта команда обновляет только
папку AI: интерфейс и кнопка требуют отдельной интеграции C.

В версии `9722cc0` обнаружена ошибка чтения HTTP-ответа с `Content-Length`:
после последнего непустого блока Python закрывает поток, а транспорт повторно
обращался к его сокету и выдавал `invalid_response`. Исправление завершает чтение
при закрытии потока и проверяет полноту ответа. Регрессионные тесты используют
настоящий локальный HTTP-сервер: короткие и длинные ответы, `Content-Length`,
chunked и обрыв тела. Код `invalid_response` сам по себе не означает неверный ключ.

### Остальные совместимые серверы

Поддерживается сервер с Chat Completions API `/v1/chat/completions`, JSON mode
(`response_format.type=json_object`), `max_tokens` и обычным текстовым
`choices[0].message.content`. API-совместимость конкретного сервера проверяется
перед демонстрацией. Поддержка такого протокола не означает, что провайдер или
модель разрешены организаторами.

Официальный пример совместимого интерфейса:
[vLLM OpenAI-compatible server](https://docs.vllm.ai/en/v0.30.0/serving/online_serving/openai_compatible_server/).
Не устанавливаем vLLM и не загружаем модель автоматически: для локального режима
нужен уже предоставленный или отдельно настроенный разрешённый сервер.

| Переменная | Значение |
|---|---|
| `MONEYGRAPH_AI_ENABLED` | `true` для включения; по умолчанию `false` |
| `MONEYGRAPH_AI_PROVIDER` | Название согласованного провайдера |
| `MONEYGRAPH_AI_MODEL` | Для профиля `openai` по умолчанию `gpt-6-luna`; для остальных обязателен |
| `MONEYGRAPH_AI_BASE_URL` | Для `openai` по умолчанию `https://api.openai.com/v1`; для остальных обязателен |
| `MONEYGRAPH_AI_API_KEY` | Только переменная окружения backend |
| `MONEYGRAPH_AI_ALLOW_EXTERNAL` | `true` только при согласованной передаче |
| `MONEYGRAPH_AI_TIMEOUT_SECONDS` | Бюджет двух запросов, 30 секунд по умолчанию, 1–120 |
| `MONEYGRAPH_AI_REASONING_EFFORT` | Только для `openai`; по умолчанию `low` для GPT-6, для других моделей не передаётся |

Локальный режим при `ALLOW_EXTERNAL=false` принимает только буквальный loopback
`http://127.0.0.1:PORT/v1` или `http://[::1]:PORT/v1`. Сетевой сервер организаторов
на другом адресе тоже требует явно разрешённой передачи и HTTPS; слово
«локальный» само по себе не делает удалённый адрес безопасным.
Для внешнего сервера обязательны HTTPS, ключ и `ALLOW_EXTERNAL=true`.
URL с паролем, query или fragment, редиректы и унаследованные HTTP-прокси запрещены.

Ключ не помещать в Git, браузер, команды с открытым значением и снимки.
На Linux можно ввести его без отображения и записи значения в историю:

```bash
read -r -s -p 'API key: ' MONEYGRAPH_AI_API_KEY
export MONEYGRAPH_AI_API_KEY
```

Другие переменные задаёт оператор backend. Повторного согласования передачи
при каждом клике не требуется; конфигурационный флаг фиксирует уже принятое
решение. При отзыве разрешения отключить флаг: проверка выполняется даже перед
чтением кэша. Псевдонимы **не анонимизируют** финансовые суммы и структуру.

## Проверки и ограничения достоверности

1. Строгая JSON-схема: лишние поля, дубли ключей, NaN, незавершённые ответы,
   неизвестные fact_ids и отсутствующие разделы отклоняются.
2. Все числа в тексте должны встречаться в значениях цитируемых фактов.
   Сохраняются точные суммы, роль, поддержка, оценка и приоритет.
3. Каждое обязательное ограничение должно присутствовать и ссылаться на свой факт.
   Действия проверяются по разрешённому перечню и доступности данных.
   Гипотезы имеют отдельное поле и явный префикс «Гипотеза:».
4. Второй вызов той же настроенной модели отдельно проверяет смысл каждого
   утверждения: например, число плательщиков нельзя назвать числом получателей.
   Отрицательный, противоречивый или некорректный вердикт не публикуется.
5. Даже второй вызов может ошибиться вместе с первым. Нет гарантии отсутствия
   галлюцинаций и нет доказательства логического следования произвольного текста.
   `human_review_required=true` всегда. На защите аналитик сверяет факты.

Подсчёт чисел не проверяет их смысл; именно поэтому введён отдельный этап
проверки. Мы не заявляем, что фильтр слов или валидные ссылки решают эту задачу.
В тесте специально есть «13 получателей» со ссылкой на «13 плательщиков»:
числовая проверка проходит, а отрицательный вердикт проверки блокирует ответ.
Это тест поведения кода при вердикте, а не доказательство качества реальной LLM.

Максимум пакета — 24 КБ; до трёх направленных путей, без всего графа и операций.
Ответ HTTP ограничен 64 КиБ; генерация — 4096 токенов, проверка — 600 для
совместимого режима или 2048 для профиля OpenAI. В OpenAI лимит включает
внутренние reasoning tokens, поэтому для отдельной проверки выделен больший бюджет.
Один общий временной бюджет используется для двух последовательных вызовов;
тайм-аут сокета обновляется на чтении. Разрешение DNS зависит от ОС, поэтому
для внешнего провайдера это не гарантия жёсткого wall-clock лимита DNS.
Сетевой адаптер рассчитан на текущий Python 3.12; проверен локальным HTTP-сервером.

Не более двух запросов объяснения одновременно на процесс. Повторный запрос
того же клиента во время расчёта возвращает `busy`; очередь безгранично не растёт.
Успехи кэшируются в памяти до 15 минут, максимум 128 записей. Ключ включает
снимок, клиента, хеш фактов, endpoint, провайдера, модель, версии и хеши инструкций.
Ошибки не кэшируются. Повторов HTTP и скрытого резервного провайдера нет.
Обновление конфигурации создаёт отдельный сервис; UI получает только безопасный
код ошибки и «AI-объяснение недоступно». Модуль не пишет запросы, ключи или
полные ответы в логи. Политику логирования внешнего провайдера надо проверить
при его выборе; клиентский код её не контролирует.

## Тесты

```bash
python -m pip install '.[serve,dev]'
python -m pytest tests/ai -q
```

Без `serve` AI-тесты пропускаются как тесты необязательной части. Два следующих
флага включают дополнительные проверки и должны быть заданы на приёмке.
Сначала создать завершённый снимок стандартной командой B:

```bash
python -m moneygraph run --data ./data --out ./out
```

Подставить выведенный каталог RUN_ID:

```bash
MONEYGRAPH_AI_SNAPSHOT_DIR=./out/runs/RUN_ID MONEYGRAPH_AI_API_TESTS=1 python -m pytest tests/ai -q
```

Последний флаг требует объединённого checkout с `moneygraph/api`. В отдельной
ветке AI можно подключить checkout C через PYTHONPATH, не редактируя его файлы.
Явно включённая проверка при отсутствии C должна падать, а не молча пропускаться.

На 2026-09-23 после добавления OpenAI-профиля выполнены **79 тестов**, без
пропусков (предыдущий прогон общего модуля — 66), в том числе:

- пять сценариев через настоящий pipeline A/B на синтетических данных;
- контекст всех 2248 клиентов выданного снимка, точные суммы и отсутствие ID в
  запросе модели; представлены сбор, распределение, несколько seed, граница, изолят;
- пропущенные значения, повреждение снимка, несогласованные показатели;
- неизвестные ссылки, выдуманные числа, обвинения, лишние поля, неверная
  доступность действий и пропущенные ограничения;
- некорректный ответ/вердикт, превышение размера, redirect, 429, 500 и тайм-аут;
- кэш, его размер, истечение срока, разделение запусков и конкурентные клики;
- профиль OpenAI, правильные поля Structured Outputs и лимита токенов,
  защита ключа от подмены адреса, отсутствие сети при проверке настроек,

  **не приёмка ещё не добавленной кнопки в браузере**.

Есть стороннее предупреждение Starlette/httpx; оно не влияет на результат.
Синтетические ответы находятся только в тестах. Реальные данные и записки
не добавляются в репозиторий.

## Что осталось перед защитой

1. C подключает endpoint и кнопку, состояния загрузки/ошибки и просмотр фактов.
2. Команда включает профиль OpenAI и вводит ключ через окружение, проверяет
   доступ командного API-проекта командой `python -m moneygraph.ai.check --live`.
3. На реальной модели вручную проверить пять сценариев, сверить каждый текст с
   фактами, выполнить минимум повторный прогон и измерить задержку. Отдельно
   проверить ответ при неизвестных данных и недоступности провайдера.
4. Проверить в браузере: клиент из очереди → «Объяснить с AI» → ссылка F… →
   исходный факт → операции. Повторный клик должен использовать кэш. При отказе
   AI обычное объяснение, граф и выгрузки остаются доступны.
